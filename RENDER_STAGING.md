# Render staging deployment guide

This guide describes the staging Blueprint in `render.yaml`. It does not deploy anything.

## Resources

The Blueprint defines four staging resources:

1. `hvac-ops-staging-db`: Render-managed PostgreSQL 16, using the free staging plan and no public database access.
2. `hvac-ops-staging-backend`: paid Starter Docker web service running Gunicorn, with `/api/health/` as its health check.
3. `hvac-ops-staging-technician-bot`: paid Starter Docker background worker running `python -m telegram_bots.technician_bot.main`.
4. `hvac-ops-staging-frontend`: React/Vite static site built from `frontend/`, with all SPA routes rewritten to `index.html`.

The backend also receives a 1 GB persistent disk named `hvac-ops-staging-media`, mounted at `/app/media`. This matches Django's current `MEDIA_ROOT` because the Docker image uses `/app` as its working directory.

## Blueprint-managed environment variables

Render supplies or generates these values automatically:

- `DJANGO_SECRET_KEY`: generated by Render.
- `DATABASE_URL`: internal connection string from `hvac-ops-staging-db`.
- `ALLOWED_HOSTS`: backend `RENDER_EXTERNAL_HOSTNAME`.
- `PUBLIC_BASE_URL`: backend `RENDER_EXTERNAL_URL`.
- `BACKEND_PUBLIC_BASE_URL`: backend `RENDER_EXTERNAL_URL`.
- `CORS_ALLOWED_ORIGINS`: frontend `RENDER_EXTERNAL_URL`.
- `CSRF_TRUSTED_ORIGINS`: backend `RENDER_EXTERNAL_URL`.
- `TECHNICIAN_API_SHARED_SECRET`: generated on the backend and copied to the bot worker.
- Worker `TECHNICIAN_BOT_TOKEN`: copied from the backend service.
- Worker `BACKEND_API_BASE_URL` and `BACKEND_PUBLIC_BASE_URL`: backend `RENDER_EXTERNAL_URL`.
- Frontend `VITE_API_BASE_URL`: backend `RENDER_EXTERNAL_URL` at build time.

The Blueprint fixes these non-secret staging values:

- `DEBUG=False`
- `DATABASE_CONNECT_TIMEOUT=5`
- `SECURE_SSL_REDIRECT=True`
- `SESSION_COOKIE_SECURE=True`
- `CSRF_COOKIE_SECURE=True`
- `SECURE_HSTS_SECONDS=31536000`
- `SECURE_HSTS_INCLUDE_SUBDOMAINS=True`
- `SECURE_HSTS_PRELOAD=True`
- `TIME_ZONE=America/Los_Angeles`
- `GOOGLE_SERVICE_ACCOUNT_JSON_PATH=/etc/secrets/google-service-account.json`
- `GOOGLE_CALENDAR_SCOPES=https://www.googleapis.com/auth/calendar`

## Values to enter manually

During the initial Blueprint creation, enter these values on `hvac-ops-staging-backend`:

- `TECHNICIAN_BOT_TOKEN`: the staging technician bot token. The worker copies this value from the backend.
- `TECHNICIAN_BOT_USERNAME`: the staging technician bot username.
- `TELEGRAM_BOT_TOKEN`: the separate staging notification bot token used by `NotificationService`. It may equal the technician bot token only if that is an intentional operator decision.

Render generates `DJANGO_SECRET_KEY` and `TECHNICIAN_API_SHARED_SECRET`; do not replace them with committed values. If the Blueprint is being synced into existing services, `sync: false` variables are not prompted again and must be entered from the service's Environment page.

## Google service account secret file

In the Render Dashboard, open `hvac-ops-staging-backend`, then add a Secret File:

- Filename: `google-service-account.json`
- Runtime path: `/etc/secrets/google-service-account.json`
- Contents: the complete staging Google service-account JSON

Do not add this file to the repository. Share the technician calendars with the service account's email address using only the permissions required by the calendar workflow.

The technician bot worker does not read Google credentials, so it does not need this secret file.

## Database and migration lifecycle

The backend receives the database's internal `connectionString`; database credentials are not committed or copied manually. `ipAllowList: []` blocks public database connections.

Render runs `python manage.py migrate` as the backend `preDeployCommand`, after a successful image build and before Gunicorn starts. A failed migration prevents the new application version from becoming active. Do not move migrations into `dockerCommand`.

## Contract PDF storage and serving limitation

Generated PDFs are written to `/app/media/contracts/`, which is covered by the persistent disk. This makes files survive backend restarts and redeploys and allows the backend to upload the local PDF directly to Telegram.

Current limitation: `config/urls.py` exposes `/media/` only when `DEBUG=True`. Staging correctly uses `DEBUG=False`, so PDF URLs such as `/media/contracts/...` are not publicly served by Django. The disk therefore provides persistence and direct Telegram delivery, but not public browser downloads. The public-URL fallback also cannot recover a missing local file until a production media-serving solution is added. Do not scale the disk-backed backend above one instance; Render disks attach to only one service instance and disable zero-downtime deploys.

## Staging setup order

1. Prepare the three manual environment values and the Google JSON file before creating the Blueprint.
2. Review resource names and plans in `render.yaml`. Keep all resources in the same Render region and workspace.
3. Create the Blueprint from `render.yaml` and enter the three `sync: false` backend values during the initial creation flow. Render can start initial resource deploys as part of Blueprint creation; `autoDeployTrigger: off` disables later commit-triggered deploys, not the initial creation.
4. As soon as the backend service record exists, add `google-service-account.json` as its Secret File. Saving the file triggers a backend deploy with the credential available.
5. Confirm the generated cross-service values: backend/frontend external URLs, `DATABASE_URL`, CORS/CSRF origins, worker backend URLs, and frontend `VITE_API_BASE_URL`.
6. Verify the database-backed backend first. If its initial deploy ran before configuration was complete, trigger a manual deploy. Confirm the pre-deploy migration succeeds and `/api/health/` returns HTTP 200.
7. Verify or manually redeploy the static frontend. Confirm deep links such as `/technicians` and `/reports` load through the SPA rewrite and API requests target the staging backend.
8. Verify or manually redeploy the technician bot worker last. Confirm it starts polling and configures the Mini App menu without starting a Django web server.
9. Perform staging-only authentication, calendar, Telegram, contract-PDF, and persistence smoke tests. Do not use production bot tokens, calendars, or customer data.

## Values assigned only after Blueprint creation

These values cannot be known in advance, but the Blueprint wires them automatically:

- Backend external hostname and HTTPS URL.
- Frontend external HTTPS URL.
- Render Postgres internal connection string and credentials.
- The derived `ALLOWED_HOSTS`, CORS/CSRF origins, public backend URLs, worker backend URLs, and frontend `VITE_API_BASE_URL`.

## Operational limitations

- The backend requires a paid Render plan because persistent disks are not available on free web services.
- The background worker also requires a paid plan; Render does not offer a free worker plan.
- The free PostgreSQL plan is suitable only for staging evaluation. Select `basic-256mb` if the workspace does not offer free PostgreSQL or the staging retention requirements exceed the free plan.
- The backend disk prevents horizontal scaling and zero-downtime deploys.
- Public PDF downloads are not available with the current Django URL configuration.
